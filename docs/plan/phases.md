# Progressive Discovery Funnel and Phases

This document records the current phase concept and the first implementation target. The funnel is intended to guide staged research, but only Phase 0.1 is currently in implementation scope. Later phase boundaries remain open to evidence from real use.

## Funnel principle

Begin with broad market discovery, then reduce the candidate set through increasingly focused checks. Spend on deeper investigation only while its result could affect suitability, cost, risk, or the recommendation. Apply ordinary screening decisions automatically, record their evidence and reasons, and bring the user in at phase checkpoints rather than after every routine step.

**Cost-aware rule:** cheap evidence first; expensive investigation only when it can still change the decision. A missing fact is not automatically a confirmed failure. Distinguish verified facts, attempted but blocked checks, unchecked questions, and evidenced exclusions.

## Cross-phase task register

Concrete follow-up actions may arise in multiple phases, so task handling belongs in [`references/shared/tasks/instructions.md`](../../plugins/de/de-stromwechsel/skills/de-stromwechsel/references/shared/tasks/instructions.md). `active.md` holds tasks that still need action; `done-YYYY.md` archives closures by closure year with a concise result and evidence or user decision. Explicit cancellation and non-applicability use distinct outcomes. Reconcile Active and Done on every update, saving a closure before removing its active entry. Apply the same rules to follow-up messages after a phase checkpoint. Localize generic field labels and statuses; keep useful German contractual terms. These refinements are agreed in [D-019](decisions.md#d-019-task-closure-reconciliation-and-language); remaining format details await validation. Provider payments use linked terms and receipt checks under [D-007](decisions.md#d-007-provider-payment-follow-up), refined by [D-020](decisions.md#d-020-conditional-eligibility-and-payment-timing). Known future conditions remain visible without blocking an earlier supported receipt check; unresolved eligibility still blocks receipt. All unresolved financial actions within phase scope require tasks under [D-011](decisions.md#d-011-financial-follow-ups-and-first-recurring-payment), including one check of the first recurring Abschlag payment. The register is passive and does not provide background monitoring or reminders.

## Phase 0 — Preparation

Phase 0 prepares a reliable account of the user's starting situation and the inputs for later research. It has two identified subphases: 0.1 As-Is Research and 0.2 Discovery Configuration. Only 0.1 is in the first implementation slice; do not create the later phase instructions in advance.

## Phase 0.1 — As-Is Research

### Objective and value

Reconstruct the user's current electricity-supply situation from available records and leave an understandable, resumable starting point for future work. Phase 0.1 should be useful on its own, even if the user does not continue to tariff discovery. Inventory existing documents where they are and record their locations; do not sort or reorganize the user's old files.

### Sources

Potential inputs include accessible local folders; current and previous contracts or confirmations; annual and final bills; price sheets and terms; meter readings; and other electricity-related documents. Archive consent covers needed contents of all file types, including local EML messages and attachments; refusal stops Phase 0.1. When a material gap remains, ask whether relevant records may be in an additional folder; after disclosure, a path supplied by the user authorizes review of all files and subfolders there for this task. Connected email is a separate optional source and requires focused, explicit permission before search. Review newly authorized evidence before deciding whether model escalation is still useful.

### Initial workflow

This sequence is a starting scope for implementation, not a mandate to create a rigid taxonomy for the user's existing files.

In OpenAI/Codex, before substantive work on a new Phase 0.1 run, recommend Luna Extra High and wait for `Continue`, allowing the user to retain their current model. Do not repeat this gate on resume. This confirms readiness, not actual model assignment. Apply the shared escalation rules below when material uncertainty remains.

1. **Choose locations:** if the current folder clearly appears to be the user's Strom project, inspect only low-cost metadata, explain why it appears suitable as both archive and workspace, and ask the user to confirm before writing files or doing deep inventory. Otherwise ask separately for the archive and work locations. With that confirmation, disclose and obtain consent to read needed file contents of any type, including local EML and attachments; stop if declined. Record the reading permission, and obtain it if older state confirms only folder roles. Warn that the working folder should be private and non-public. Reuse a saved location only when accessible and explicitly confirmed with the required reading scope. A cloud-provider name is an access route, not a path; if files are inaccessible, ask for a usable local path, mount, or upload.
2. **Create the skill workspace:** in the selected work folder, create or reuse `de-stromwechsel/internal/` for agent-managed state and `de-stromwechsel/reports/` for readable reports. Year-based folders for documents the skill handles sit at the same level as `de-stromwechsel/`; reuse existing folders where suitable and create a year folder when a new document needs to be stored. This applies to documents the skill handles from this point forward, not to the user's old archive. Do not copy old source documents into the workspace as part of inventory.
3. **Inventory in place:** inspect accessible folders and file metadata to learn how the archive is arranged, identify likely electricity documents, and record their original paths. Start a working snapshot after this initial inventory and update it after meaningful review groups, before additional lengthy passes. If existing records are already grouped by year, start with the newest relevant documents and expand to establish documented history or resolve gaps and conflicts. If not, search broadly enough to find the relevant records without deep-reading every file automatically.
4. **Estimate extraction effort:** identify text-searchable files, image-only scans, and any available OCR companions where tools allow. Before bulk OCR or deep reading of a large scan-heavy archive, tell the user the estimated scope and ask whether to proceed. If the user declines, continue with searchable and already-extracted evidence and record the limitation. Exact thresholds remain open.
5. **Identify and reconcile:** review the records that can establish the current supply and relevant history; note likely duplicates, conflicting facts, missing materials, and which versions appear current or superseded. Use older annual/final bills and key contract records to establish history; expand other reading where needed to establish a transition, resolve a conflict, or clarify a material term.
6. **Recover material source gaps:** before the final checkpoint, ask whether relevant records may be in an additional folder and whether the user permits a focused connected-mailbox search. A user-provided folder path, after disclosing the read scope, authorizes review of its contents, including all file types and subfolders, for the task; do not ask per file. The extraction-effort checkpoint still applies. Connected-mailbox access requires separate explicit permission and a focused search. Review newly authorized sources before deciding whether Sol escalation remains useful. Wait for a response to pending access questions; silence is not permission. If permission is declined or access is unavailable, continue from authorized sources and record the limitation.
7. **Save a current-state record:** create a user-readable report, document-based `history.md`, and a minimal resumable state in the skill workspace. Link to source documents and record where each was found; do not sort, move, rename, or otherwise reorganize the old source archive.

### Evidence and user-facing language

Use the strongest applicable evidence after considering its directness, recency, completeness, and relevance. When one source clearly controls, state the working fact or default and the reason, while retaining older or weaker values as contextual history with provenance. Do not turn them into equal unresolved choices. For consumption, a recent complete, representative annual bill or `Abschlussrechnung` normally supplies the working basis unless there is stronger contrary evidence; disclose the billing period and any estimated component, and invite correction. A sub-interval included in the bill total is not a separate annual consumption candidate. Verify material OCR-derived values visually when feasible, or mark the limitation.

Reports, history, task lists, and user-facing checkpoint messages use the language of the first substantive request in the run. Internal state and inventory are written in English. When listing inventory totals, distinguish original documents from OCR companions and do not double-count companion pages as additional source pages.

### Task register

Phase 0.1 uses the [shared task instructions](../../plugins/de/de-stromwechsel/skills/de-stromwechsel/references/shared/tasks/instructions.md) when current-state research identifies a concrete follow-up. For provider payments or credits under a concrete contract, it creates linked eligibility and receipt follow-ups. Phase 0.1 includes tasks from the current active contract in full and predecessor-contract tasks only within the current month plus three preceding calendar months; this Phase 0.1 scope is recorded in [D-009](decisions.md#d-009-phase-01-task-horizon). Record the reading, photo, archive save, and direct Netzbetreiber submission as one dated follow-up when the active contract establishes a real reading trigger; supplier submission is optional. Minimum-term expiry alone does not establish an end-of-supply date. Whether the register's remaining format and broader usefulness are suitable for later phases remains open for validation.

### Information to establish

Where evidence permits, record the current provider and tariff; contract start and known end or termination dates; Arbeitspreis and Grundpreis; known bonuses and material contractual limits; historical consumption; meter details and readings; previous providers and supply periods; relevant documents; and missing, uncertain, or conflicting information. Never fill gaps by invention. Separate document-supported facts from user reports and preliminary inferences.

### Supply history

Maintain `de-stromwechsel/history.md` using the [shared history instructions](../../plugins/de/de-stromwechsel/skills/de-stromwechsel/references/shared/history/instructions.md), by [D-013](decisions.md#d-013-document-based-supply-history). Use documented annual/contract cycles as rows, including separate years with the same supplier and a current period without a bill yet. Reconcile confirmations and bills; combine consecutive, non-overlapping invoice slices within one cycle without summing corrections or cumulative duplicates. A closing estimated reading makes the period consumption estimate-based; an intermediate estimate alone does not if actual endpoints and continuity establish the total. See [D-014](decisions.md#d-014-history-period-aggregation-and-consumption-labels). The table and its linked reference sections both run newest/current to oldest. Record consumption and the total electricity cost for the period before deductions for paid advances, when documented. History does not record settlement balances, individual refunds/debits, or payment status. History can cover older periods beyond the task horizon without generating old tasks. Link it from the report and state; expose gaps rather than imply complete coverage.

### Repeated runs

**Proposed:** later runs should reuse saved state, look for changes, and avoid reprocessing a full archive without reason. Verify that a linked report still exists before treating its checkpoint as complete; if it has been removed, explain that the saved state is only an index and rebuild the current report from accessible evidence. The initial implementation uses a concise Markdown `internal/state.md` index pointing to the report and a separate English `internal/inventory.md`; detailed fields remain provisional. Complex synchronization is out of scope for the first implementation.

### Boundary with future market research

Phase 0.1 establishes actual contract dates and terms where available. It does not set a binding future quotation date. The handoff floated using a user-supplied date or a supported approximate date for market research, with roughly three months ahead as one possible default if no date is known. This remains a **proposal for Market Discovery**, not a Phase 0.1 rule, and must never be represented as a legally confirmed switch date. A calculator's date limits and the chosen scenario need to be recorded when that later phase is designed.

### Current status

The user accepted Phase 0.1 v1 after the 2026-11-06 rerun. The run paused for source-access answers, reviewed newly authorized email evidence, kept an unconfirmed receipt as an active task, and saved the final checkpoint without beginning a later phase. The task-closure, localized-metadata, conditional-eligibility, and source-first escalation rules were exercised in this phase. Phase 0.2 is not implemented; its scope remains to be designed.

## Checkpoints and resumability

At the end of each completed phase, save its result and provide a short checkpoint that tells the user what was examined, what was found and remains unknown, which material decisions or exclusions were made and why, and what phase is next. Then stop so the user can review, continue, refine criteria, request more research, repeat part of the phase, or override a decision.

Final user checkpoints are phase boundaries. Interim working snapshots are progress saves and do not ask for approval. Specific consent rules still apply, including the user's permission before email search. Phase 0.1 treats the old source archive as read-only and does not reorganize its files.

Saved artifacts should let a later run identify the completed phase, research performed, verified facts, open questions, decisions, and next action without depending on chat history alone. The [working checkpoint instructions](../../plugins/de/de-stromwechsel/skills/de-stromwechsel/references/shared/checkpoints/instructions.md) define separate English snapshots and `internal/checkpoints/registry.md`, without checkpoint logs or links in state. Retain one current snapshot and one completed archive; rotate only after checking durable artifacts. Resume partial work from the indexed snapshot. Detailed state/inventory fields remain open for validation.

## Shared model escalation

Use [shared escalation criteria](../../plugins/de/de-stromwechsel/skills/de-stromwechsel/references/shared/model-escalation/instructions.md) across phases and the [OpenAI procedure](../../plugins/de/de-stromwechsel/skills/de-stromwechsel/references/shared/model-escalation/openai.md) in Codex/OpenAI. Resolve material gaps in authorized sources first, asking for permission when needed, then reassess whether a remaining interpretive uncertainty could change a conclusion or action. Request Sol Medium only through a documented escalation/model-selection capability; actual assignment need not be verified. Use High only for a material doubt remaining after Medium. If no request mechanism exists or a request fails, warn and continue with the selected model. A phase may explicitly require an attempt for a step; no such unconditional step is currently required by Phase 0.1. A separate test prompt may force the trigger to exercise runtime capability, without authorizing access to new sources. Do not prebuild other provider adapters.

## Assessments, exclusions, and overrides

**Agreed direction:** the skill owns a standard assessment method and automatically applies its exclusion criteria. It records the criterion, evidence, and rationale rather than asking the user to approve each routine exclusion. It distinguishes a confirmed incompatibility from insufficient evidence. A user may restore an excluded candidate; preserve the original finding and reason alongside the user's override, and do not erase the identified risks.

Potential provider assessment topics include unusually high Abschläge, delays in Schlussrechnung and Guthaben payment, their combined cash-flow effect, and customer reports. Their source set, weighting, severity rules, and numeric thresholds are **open for validation**. A personal preference can shape the user's own decision without becoming a universal factual risk rule.
