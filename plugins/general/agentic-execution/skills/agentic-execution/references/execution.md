# Execute a batch and advance

Verify current Planning Acceptance per [Execution planning](execution-planning.md). Record/read back Current Batch start before substantive work, unless already recorded for its current activation. Use [Task Ledger](task-ledger.md) for events and [Evidence and checkpoints](evidence-and-checkpoints.md) for evidence and versioning.

## Execute each Single Focus Step

1. Verify actual dependencies and valid earlier results; stop affected work on invalid inputs or reserved decisions. When a recorded material risk trigger fires or evidence contradicts an assumption, reassess affected work under [Changes and corrections](changes-and-corrections.md#ordinary-operational-changes) before continuing affected Steps; a trigger is not itself authorization. Use applicable RT IDs and record actual trigger/disposition and material autonomous choices under [Risk Tripwires](risk-tripwires.md) and [Agentic Decisions](agentic-decisions.md). Record the actual E-Step start promptly before its substantive work; correlate the outcome with that Step and attempt, reconciling any recorded start on recovery. A shared event may cover batch/first-Step start when they actually coincide.
2. Execute authorized work using the applicable accepted Tools & Skills; verify needed capabilities and follow their relevant instructions within existing authority and gates. When a trigger or contradicted assumption becomes known during work, apply the same reassessment before further dependent action (including pending job/review reconciliation where needed). Preserve failures, skipped checks and limitations; capture material autonomous decisions promptly when made, not only after the Step. For potentially non-idempotent actions persist/read back authorized intent, target and expected result before acting; reconcile actual outcome before retry.
3. Record actual output/checks, input and implementation versions and evidence in Task Ledger, including material Tools & Skills usage, deviations and relevant workflow artifact references. Material changes to executable scope or prerequisites require renewed Planning Acceptance before affected work; strategy failure/earlier defect → [Changes and corrections](changes-and-corrections.md).

### Long-running work (when applicable)

Plan proportionate verification before expensive/irreversible runs: actual executable/environment identity, input versions, permissions and data isolation, clean output destinations, fresh versus reused work, completion/error signals, proportionate no-progress reassessment criteria and recoverable evidence. Cheap preflight must test the real path/assumptions; disclose changes to execution copies or instrumentation and verify that intended work actually ran. Keep local/private evidence access-controlled. No universal harness, telemetry or mandatory polling interval.

Apply [Pending work and waiting](waiting-and-continuation.md#pending-work-and-waiting). For a long job that may outlive its call/turn, the pending Task Ledger record includes input/command identity, output/evidence location and recovery basis; add the available process/session handle or receipt promptly. Reconcile uncertain launch before retry even for costly read-only computation. Prefer authorized deterministic in-tool monitoring over repeated model calls when supported and safe; use the applicable harness guidance for concrete wait controls. Preserve actual exit status and results; no speculative token attribution. Recover existing results/checkpoints on interruption rather than blindly rerun.

## Execution Acceptance and checkpoint

Record the actual work outcome before submitting it for Execution Acceptance; distinguish work completion or partial/failed outcome from acceptance and checkpoint. If corrections require further work, record material correction starts and outcomes before resubmission. Give the **same Combined Execution Batch Reviewer** (or its verified fresh same-role replacement per Reviewers when the retained context is lost/incompatible, including harness handoff) recoverable actual implementation/artifacts, evidence, Task Ledger, effective requirements and plan changes, applicable risk definitions/actual dispositions and relevant Agentic Decisions history; apply [Reviewers](reviewers.md) and [Review protocol](review-protocol.md). Require explicit acceptance of technical/domain substance and completeness/truthfulness of required work, checks, evidence and tracking (including compliance with the applicable [Task Ledger timestamp policy](timestamp-policy.md#timestamp-capture)), including evidence of actual compliance with applicable accepted strategic Tools & Skills choices and human-required workflows, and the authorization and verification of material deviations. Assess applicable material decision coverage, provenance, authority and risk checks/dispositions against evidence. Verify conditional applicability and material workflow outputs from primary evidence, not mere mentions in the Ledger. Assess material compliance with the [Progress invariant](../SKILL.md) and [Waiting discipline](waiting-and-continuation.md#pending-work-and-waiting) within the applicable governing revision and submitted scope, using available evidence. Evaluate the purpose of operations and whether the enabled next action was taken; identify demonstrated unjustified activity, waiting substitution or unsupported cessation, not merely particular commands. Apply the review protocol's disposition of historical process deviations; do not require exhaustive raw-session replay, additional telemetry or a separate gate. Correct, rerun affected checks and resubmit until accepted. Renew Planning Acceptance first if material plan changed.

After acceptance verify/create scoped durable checkpoint per Evidence and checkpoints. Record/read back acceptance, evidence and checkpoint in Task Ledger; pending until verified. Recover exact accepted content if interrupted; no substitution. Before advancement, verify material post-submission lifecycle events and disclosed deviations against actual evidence. If a newly identified blocking process finding affects this batch's acceptance or checkpoint, stop advancement. If the checkpoint is not yet verified, correct the affected Current Batch and renew its affected acceptance before checkpointing (renew Planning Acceptance if required). If already checkpointed, preserve its historical scope: for process-only disposition obtain explicit independent closure and renewed affected acceptance in the existing batch review (same reviewer or verified replacement), linking the later disposition; for substantive defects follow the new correction batch rules in Changes and corrections. Retire reviewer and advance only after checkpoint; follow [Execution planning](execution-planning.md) to reconcile suspended dependents before ordinary Next Batch promotion. Earlier batches are historical; use correction batches. When no work remains route to [Final acceptance](final-acceptance.md).

## Task Ledger

Use the lifecycle-wide [Task Ledger](task-ledger.md) for actual work, pending external intent/outcome and recovery pointers. Do not duplicate full decisions/reviews or count planned checks as performed. Reconcile on [Recovery](state-and-recovery.md).
