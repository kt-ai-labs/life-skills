# Recovery, handoff and termination

Restore from existing records and actual state; no state store or exclusive-control declaration. [Start and resume](start-and-resume.md) owns invocation, scope and authority. Never initialize over lost records. Honor restrictions before writes.

## Reconcile and resume

Honor human restrictions immediately. Inspect existing records read-only, recover and reread the governing Skill entrypoint under [Start and resume](start-and-resume.md#skill-identity-and-continuity). If recovery is blocked, report it and stop affected work; authorized restriction handling and read-only reconciliation of pending operations remain possible.

1. Read the relevant request/material dialogue, decisions and root Task Ledger records to establish the actual phase, effective definition, restrictions, approvals, launch and confirmed profiles (as far as actually created at the recovered stage). When recovering an already launched unfinished Task for continuation (including after context compaction in Execution or during Definition re-entry), establish the effective definition from authoritative version-specific decisions and acceptance evidence, and reread the complete effective Task Brief and Task Plan from those governing versions, not compacted summaries, to restore the problem, intended outcome, objectives and strategy before continuing ordinary work or advancing a lifecycle gate. If reconciliation changes the effective version of either artifact, reread that complete governing artifact before dependent work. Recover applicable governing Risk Tripwires snapshot and relevant live RT definitions/status (distinguish pending amendments) and relevant AD entries/dispositions under their contracts; do not require complete growing AD/RT rereads solely due to compaction. Restore any pending definition re-entry before resuming Execution; read its current drafts separately without treating them as effective or approved. In Definition read the current Brief/Plan drafts, D00 plan, Context index, pertinent Assignment reports and reviews as applicable. Recover operational state from the relevant portions of the Execution Plan, Task Ledger, reviews, evidence, checkpoint pointers and other records; use the recovery pointer for navigation, not as independent proof or a complete inventory of outstanding work. Reconcile it against current authoritative records and actual state; a missing, stale, contradictory or incomplete pointer does not establish that no gate, obligation or operation is pending. Expand reads as needed to establish all applicable gates, obligations, dependencies, pending operations and actual state, including full history when required. Preserve any existing stricter review policy. If an active Task has not been authorized to adopt a release's changed pending-gate behavior, preserve its existing gate requirements or obtain authorization before applying the change. If records are absent, distinguish never-created bootstrap from loss using history and actual work. Initialize only genuinely never-created files (Task Ledger during initialization, derived Execution Plan only after durable launch); reconcile interrupted legacy adoption per [Task Ledger](task-ledger.md#legacy-adoption). Never create an empty Ledger to replace lost history. Recover lost governing content/decisions with real provenance, not empty replacements or guessed authority.
2. Inspect history, working tree (including staged/untracked files), actual outputs, external action outcomes and concurrent changes. Preserve unrelated work. Reconcile records and actual versions, independent decisions and permissions; do not infer from memory or labels.
3. Restore last verified gate, active/suspended batch IDs and dependency order, open findings, effective versions and next bounded action. Distinguish not started, partial, performed-unverified, reviewed, checkpointed. Finish only missing supported bookkeeping and proceed. Repeat only affected work if safe and needed, not accepted computation because context changed. Missing private artifacts require authorized access and version/fingerprint checks or verified recomputation if safe; never publish them for recovery.
4. For uncertain outcomes of potentially non-idempotent actions inspect recorded authorized intent, actual external truth and expected result; block affected action if outcome remains unknown rather than repeat. If required history, authorization or gates cannot be verified, block affected work.
5. Persist/read back supported transitions; reconcile Task Ledger event IDs, partial writes and current pointer with actual authoritative records per [Task Ledger](task-ledger.md); reconcile required AD history and applicable risk records against actual authoritative evidence, record material recovery and continuation events and any material autonomous recovery decisions, then report recovered state and proceed. New chat/harness alone does not reset approval or Discovery.

## Pending review and checkpoint

Restore pending round records and actual host invocation state before retrying or changing gates. If established that a prepared round has not been invoked and its prerequisites remain valid, invoke it; do not prepare it again. For an existing live invocation or job, recover its available handle/receipt or other verified identity, current restrictions and evidence, then continue via [Pending work and waiting](waiting-and-continuation.md#pending-work-and-waiting); a yield, timeout or economical-wait blocker alone is not termination, failure or permission to duplicate work. If actual state cannot be established, reconcile or block under the applicable recovery rules. Apply [Reviewers](reviewers.md) to lost or incompatible context (verify old invocation stopped, fresh independent replacement under confirmed profile, preserve lineage). No late superseded acceptance. Apply [Review protocol](review-protocol.md) to recover actual response and scope. Unknown effective settings are handled only by the profile policy, never by guessed review provenance.

For valid reviewed-but-uncheckpointed work recover exact accepted content and verify/complete checkpoint per [Evidence and checkpoints](evidence-and-checkpoints.md). If exact accepted content is unavailable, integrity stop. For historical accepted checkpoint with missing or invalidated review proof, recover and verify the original decision if missing, or independently revalidate pinned historical scope and append actual new dated decision; no backdating or rewritten checkpoint. An invalidated decision cannot be restored merely because its response is available. If legitimately possible use new correction/revalidation batch to establish current obligation; otherwise integrity stop. Block dependent acceptance until resolved. Recover interrupted final reviews/checkpoint/completion by same-state reconciliation per [Final acceptance](final-acceptance.md); do not rerun valid reviews.

## Pause, stop, withdrawal, abandonment

- **Paused:** resumable when still authorized and explicit authorized Resume received. **Stopped/withdrawn:** read-only until authorized human resolves restriction; stop is not automatically abandonment or renewed authorization. Immediately stop affected work on any such instruction; safely suspend/cancel in-flight work and reviews where authorized and possible, or record unresolved activity. Persist/read back the restriction, its scope and in-flight state in decisions and applicable Task Ledger event/pointer if permitted; honor it even if recording is interrupted or forbidden. Do not assume permission for bookkeeping after withdrawal. If known termination/restriction is not durably recorded, reconcile it with an authorized human before ordinary work; missing records never lift it.
- **Abandoned:** terminal, explicitly human-directed decision to leave unfinished Task rather than resume. Confirm intent/authority only if unclear. Stop or safely reconcile in-flight reviews, writes, jobs and non-idempotent actions; record any unresolved outcome, never claim it ended without evidence. No ordinary execution afterward. With authorization, preserve actual current state, effective definition, partial/unreviewed work, open findings, incomplete gates, known local/remote versions, evidence locations and human decision in existing decisions and (if present) Task Ledger; a scoped preservation commit is optional and not an accepted checkpoint. Do not publish private material or stage unrelated work. Record abandonment and read back the authorized decision and Task Ledger event; if permission to write is absent, report restriction and pending archival bookkeeping rather than invent durable status.
- **Completed:** both final gates and checkpoint verified; never reopen. Abandoned is not Completed and cannot be resumed or retroactively accepted. Earlier accepted batch records remain historical. A new Task may explicitly reference either history and present work state; define its own scope, source authority, validation of inherited partial results and approvals. Never inherit launch, waive unverified prerequisites, roll back abandoned work by default or rewrite the old Task. A requested successor can be defined after the old Task's termination state is reconciled; any unresolved in-flight action or uncertain outcome blocks affected successor work until safely resolved. Do not assume closure merely because a new folder exists.

Use actual conflict protection from Start and resume. Preserve historical Tasks even when a new Skill release changes defaults or runtime behavior.
