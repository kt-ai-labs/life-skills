# Task Ledger — actual lifecycle history

Maintain one logical, root-level `task-ledger.md` from authorized Task initialization before D00 through completion or abandonment. Use the existing Task Directory and authorized storage; see [Task artifacts](task-artifacts.md) for privacy, source and record boundaries. The Ledger is not a second plan, approval record, review response store, telemetry service or authorization to perform work. Keep decisions, queue/status, actual review responses and evidence authoritative in their existing records; link them instead of duplicating content or creating a second competing state. No derived Execution Plan or substantive Objective execution before explicit launch.

## Events and identity

Append material actual events with stable Task-local IDs `LE001`, `LE002`, etc. (minimum three digits, extending naturally past LE999). Allocate the next number after the highest actual event ID (not IDs merely mentioned in references), in append/recording order. Never reuse or renumber. Each new event has actual UTC time in `YYYY-MM-DD HH:mm:ssZ` when obtainable from a reliable clock/event source. If actual time is unknown or only partly known, explicitly label that precision/unknown; never invent seconds or substitute commit/push time. Distinguish later recording time when material. IDs do not imply chronology of occurrence. Link related start/outcome events by stable operation identity and, where useful, LE-ID. Correct material errors by append with a new ID and reference, not silent rewriting.

Record scope (Task, definition cycle, D/B/E/O IDs, review round or other stable operation), action/outcome, meaningful actor, versions, actual evidence/checks/limitations, dependency effects and authorization pointers where applicable. Distinguish intent/preparation, actual invocation/start, partial/performed-unverified, failed/blocked/interrupted, accepted and checkpointed. Record actual outcomes, not planned ones.

```markdown
- LE001 | 2026-01-01 09:00:00Z | Task initialized; governing revision: [decision record](01-task/decisions.md).
- LE002 | 2026-01-01 09:01:00Z | D00 started.
- LE003 | 2026-01-01 09:05:00Z | D00 completed; start LE002.
```

Illustrative only; actual record links and times must be real. Keep a concise current recovery pointer: effective definition/phase, current assignment/batch and suspended identities, pending operations, open findings and next action, with relevant record/LE references. Update pointer without erasing history or treating it as independent authority.

## Recording and transitions

Record material starts and outcomes promptly throughout the lifecycle: initialization and runtime continuation, D00/Discovery assignments, independent review preparation/invocation/response and decisions/correction dispositions, material human decisions/approvals/launch, execution batches and Steps/results, substantial long jobs and external actions, re-entry and suspensions, checkpoints/pushes, recovery, closure or termination. Keep event granularity proportionate; a single event can record related transitions that actually occurred together. Do not log every tool call, edit, token, routine check or poll. For time-sensitive human or host events observed before authorized initialization, record known actual times after initialization, not guesses.

Before substantive assignment or batch work, persist and read back required current status and start event (the actual transition into work, not a claim that work has already been performed); for potentially non-idempotent actions and long jobs/reviews, preserve pending intent and recovery basis before invocation as required by the owning phase. Intent is not actual invocation; record the actual start/receipt and outcome promptly when observed. Reuse verified records; do not interpose extra checks merely for the Ledger. Gate authority and required read-backs remain in the owning contracts. A partial write is recoverable: reconcile actual records, avoid duplicate events and finish only missing supported bookkeeping before dependent work. Do not backfill fictional times or results. Local persistence is not remote visibility; no mandatory per-event commit/push. Honor authorized checkpoint/publication cadence.

## Legacy adoption

Existing Tasks remain on their pinned governing release by default. Never automatically migrate or rename records, modify historical accepted snapshots, or reopen Completed/Abandoned Tasks. For explicit authorized adoption by an unfinished Task, preserve the prior governing version, any existing Execution Ledger and its exact recoverable content (including current uncommitted material), record the mapping and adoption in decisions, and establish one active root Task Ledger before dependent work. If a legacy Ledger exists, include a clearly labeled historical pointer to its exact recoverable content and original location; retain it read-only, with relative links interpreted from that original location. Do not copy its history into a second editable record or fabricate LE-IDs or timestamps for legacy events. Start new IDs after any actual existing LE maximum; if none start LE001. The root Ledger is the only active Ledger; the preserved legacy record is historical evidence. If no legacy Ledger ever existed, initialize the root Ledger with actual adoption event and known prior record pointers, not reconstructed history. Reconcile partially completed adoption without duplicate histories/events; block if original content, authority or compatible gates cannot be established. Follow [Start and resume](start-and-resume.md#skill-identity-and-continuity) for affected gate verification and approvals. Preserve previously confirmed reviewer mappings and their documented scope during adoption per [Reviewers](reviewers.md); no automatic configuration changes.
