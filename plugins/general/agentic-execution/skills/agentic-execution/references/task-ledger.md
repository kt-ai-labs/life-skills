# Task Ledger — actual lifecycle history

Maintain one logical, root-level `task-ledger.md` from authorized Task initialization before D00 through completion or abandonment. Use the existing Task Directory and authorized storage; see [Task artifacts](task-artifacts.md) for privacy, source and record boundaries. The Ledger is not a second plan, approval record, review response store, telemetry service or authorization to perform work. Keep decisions, queue/status, actual review responses and evidence authoritative in their existing records; link them instead of duplicating content or creating a second competing state. No derived Execution Plan or substantive Objective execution before explicit launch.

For a new Task, before D00, persist/read back the initialization event and governing revision pointer. If initialization was interrupted, use the authorized scope, governing decision and actual durable history to complete only missing bootstrap records: reuse an existing initialization event, recover missing history if it once existed, and record a late event only with supported actual timing. An empty or partial file is not proof that no earlier events existed. Never overwrite lost history or create duplicate initialization events.

## Events and identity

Append material actual events with stable Task-local IDs `LE001`, `LE002`, etc. (minimum three digits, extending naturally past LE999). Allocate the next number after the highest actual event ID (not IDs merely mentioned in references), in append/recording order. Never reuse or renumber. Each new event has actual UTC time in `YYYY-MM-DD HH:mm:ssZ` when obtainable from a reliable clock/event source. Follow the timestamp capture policy below. IDs do not imply chronology of occurrence. Link related start/outcome events by stable operation identity and, where useful, LE-ID. Correct material errors by append with a new ID and reference, not silent rewriting.

Record scope (Task, definition cycle, D/B/E/O IDs, review round or other stable operation), action/outcome, meaningful actor, versions, actual evidence/checks/limitations, dependency effects and authorization pointers where applicable. Distinguish intent/preparation, actual invocation/start, partial/performed-unverified, failed/blocked/interrupted, accepted and checkpointed. Record actual outcomes, not planned ones.

```markdown
- LE001 | 2026-01-01 09:00:00Z | Task initialized; governing revision: [decision record](01-task/decisions.md).
- LE002 | 2026-01-01 09:01:00Z | D00 started.
- LE003 | 2026-01-01 09:05:00Z | D00 completed; start LE002.
```

Illustrative only; actual record links and times must be real. Keep a concise current recovery pointer: effective definition/phase, current assignment/batch and suspended identities, pending operations, open findings and next action, with relevant record/LE references. Update pointer without erasing history or treating it as independent authority.

## Deterministic append helper

For new Tasks, initialize the authorized ledger with a heading and a concise current recovery pointer before a final `## Events` section; put actual event rows in that final section, one event per line in the illustrated format. The current pointer can still be updated independently; the history is append-only. Prefer the pinned Skill's [ledger-append.py](../scripts/ledger-append.py) for actual event append where the authorized local shell has Python 3.8+ and the existing file is compatible. Resolve the script relative to the actual governing Skill root, not an arbitrary global version. It requires no additional package. Do not initialize a missing or lost ledger by calling this script; establish initialization/recovery as above. No automatic migration or rewriting of legacy records.

Pass the authorized ledger path, one meaningful single-line actual event (include scope, actor, references, provenance and outcome as applicable), and the correct timing mode. Quote arguments safely using the supported shell; do not expose restricted content in command lines/tool logs. If that would violate storage/disclosure constraints, use the authorized manual method instead.

```sh
python "<governing-skill-root>/scripts/ledger-append.py" "<task-dir>/task-ledger.md" --time-kind now --event "D00 started; scope: orientation."
```

- `now`: only for a contemporaneous Executor-controlled transition; capture UTC during the append. If capture is needed earlier than persistence, obtain and retain the actual time at the boundary, then use `captured`.
- `captured --timestamp "YYYY-MM-DD HH:mm:ssZ"`: already captured reliable actual time, including authoritative external occurrence time; identify the source in the event when relevant.
- `observed`: actual receipt/observation now, or pass its previously captured full UTC with `--timestamp`; the helper labels the event Observed. Do not claim unobserved remote occurrence; state unknown remote time when relevant.
- `historical --timestamp ...`: recovered known full time or justified partial precision/`unknown`; supply `--reason` for partial or unknown and preserve provenance. Never use `now` for retrospective events. If a capture was avoidably missed, disclose it and correct behavior under the timestamp policy.

The helper allocates the next actual LE-ID from canonical history (not incidental mentions), captures current UTC only as specified, validates input and history shape, appends without rewriting prior bytes, flushes, reads back and emits JSON with `event_id`, `timestamp`, `time_kind` and `status: appended`. A successful result establishes that local event append/readback, not the truth of the event, independent acceptance, current pointer updates, other records or remote visibility. Reuse its ID/time in corresponding records without redundant clock/append probes; still verify the owning gate's remaining facts.

On any failure or lost receipt, inspect the actual history before retrying, including whether the intended event was already appended or a partial/conflicting write occurred. Never blind-retry or duplicate an event. The helper is deliberately single-writer, not a transaction manager, lock or concurrency guarantee; retain existing competing-write handling. If Python/shell use is unavailable, the format is incompatible, or the helper cannot be used safely, use the existing manual append/timestamp/readback contract with the same authority and semantics. Reconcile ambiguous history or block if necessary; do not convert old files just to use the helper. No extra gate or per-event commit is introduced.

## Timestamp capture

For material events occurring during current work (including recovery and review transitions), actively obtain and capture UTC at the event boundary, using a reliable host/tool event timestamp or an available clock (for example `date -u '+%Y-%m-%d %H:%M:%SZ'` where supported). For Executor-controlled transitions capture the time contemporaneously with the actual transition; for external operations prefer their authoritative event timestamp, otherwise capture the time the start/receipt/result is actually observed and label it as such, rather than claiming the unobserved remote occurrence time. Do not defer capture until retrospective bookkeeping. Where a material human or host event precedes authorized record creation, retain the available event/observation time without unauthorized writes; persist only when authorized. Preserve captured times through pending state and recovery. Persist promptly with the corresponding event; reuse the same verified timestamp for genuinely coincident transitions and across records describing the same event. Do not timestamp routine tool calls or repeatedly query the clock while waiting; capture material events when they occur or become known, without delaying human restrictions, creating extra gates or interrupting genuine waiting.

Use partial precision or `unknown` only for a time that genuinely cannot be established from available reliable evidence, such as a historical/recovered event or unavailable time source; state the reason briefly. Do not use `unknown` as a substitute for obtaining an available contemporaneous timestamp. If remote occurrence time is unavailable but receipt/observation is known, record the known time explicitly as the observed event and label the remote occurrence time unknown if relevant. A receipt does not establish a remote start or completion unless its content does. For recovered events distinguish original occurrence, earlier observation (if known) and current recovery/recording; capture current material recovery events under this same policy. If later recording time is material, label it separately, never as the occurrence. Never invent seconds, relabel a later clock reading as the earlier occurrence, or substitute commit/push time for an unrelated event. Missing historical timestamps do not justify rewriting accepted history; append supported corrections under Events and identity. No exhaustive historical timestamp search or repeated probes solely to fill an unknown. If a current capture was missed despite available reliable evidence, record the supported time or honest uncertainty and the omission; correct the capture behavior rather than fabricate provenance. In existing tracking/acceptance checks, identify demonstrated avoidable omissions within the submitted scope and governing revision, using available evidence and the normal severity/correction rules. A justified unknown or partial historical time is not itself a finding; do not retroactively impose a newer capture requirement or require additional instrumentation to prove every clock read.

## Recording and transitions

Record material starts and outcomes promptly throughout the lifecycle: initialization, runtime continuation and explicit Skill adoption, D00/Discovery assignments, independent review preparation/invocation/response and decisions/correction dispositions, material human decisions/approvals/launch, execution batches and Steps/results, substantial long jobs and external actions, re-entry and suspensions, checkpoints/pushes, recovery, closure or termination. Keep event granularity proportionate; a single event can record related transitions that actually occurred together. Do not log every tool call, edit, token, routine check or poll, or the act of recording a Ledger event itself. For time-sensitive human or host events observed before authorized initialization, record known actual times after initialization, not guesses.

Before substantive assignment or batch work, persist and read back required current status and start event (the actual transition into work, not a claim that work has already been performed); for potentially non-idempotent actions and long jobs/reviews, preserve pending intent and recovery basis before invocation as required by the owning phase. Intent is not actual invocation; record the actual start/receipt and outcome promptly when observed. Reuse verified records; do not interpose extra checks merely for the Ledger. Gate authority and required read-backs remain in the owning contracts. A partial write is recoverable: reconcile actual records, avoid duplicate events and finish only missing supported bookkeeping before dependent work. Do not backfill fictional times or results. Local persistence is not remote visibility; no mandatory per-event commit/push. Honor authorized checkpoint/publication cadence.

## Legacy adoption

Existing Tasks remain on their pinned governing release by default. Never automatically migrate or rename records, modify historical accepted snapshots, or reopen Completed/Abandoned Tasks. For explicit authorized adoption by an unfinished Task, preserve the prior governing version, any existing Execution Ledger and its exact recoverable content (including current uncommitted material), record the mapping and adoption in decisions, and establish one active root Task Ledger before dependent work. If a legacy Ledger exists, include a clearly labeled historical pointer to its exact recoverable content and original location; retain it read-only, with relative links interpreted from that original location. Do not copy its history into a second editable record or fabricate LE-IDs or timestamps for legacy events. Start new IDs after any actual existing LE maximum; if none start LE001. In either case record/read back the actual adoption event and governing revision pointers in the root Ledger (including the prior record pointer when applicable), not reconstructed initialization or execution history. If D00 has not yet started, the verified adoption/bootstrap record suffices; preserve the original initialization facts only when supported by actual evidence. The root Ledger is the only active Ledger; the preserved legacy record is historical evidence. Reconcile partially completed adoption without duplicate histories/events; block if original content, authority or compatible gates cannot be established. Follow [Start and resume](start-and-resume.md#skill-identity-and-continuity) for affected gate verification and approvals. Preserve previously confirmed reviewer mappings and their documented scope during adoption per [Reviewers](reviewers.md); no automatic configuration changes.
