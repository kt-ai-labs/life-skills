# Evidence, versions and checkpoints

Use existing Markdown records, Git history, working tree and actual artifacts as the durable state. No mandatory snapshot.json, state DB, full working-tree copy or additional verification-contract file.

## Evidence

Each mandatory Objective has Expected Evidence and Verification in Task Plan; map actual evidence to that O-ID and relevant Steps/batches. Keep raw or retrievable outputs, source versions, input parameters, commands/method, check result and limits where relevant. Record actual executed code/data version, not just the latest modified file. Failures, negative or inconclusive valid results are evidence; missing tests are missing, not passed. Distinguish a summary from underlying evidence. Use local relative links or durable external identifiers with appropriate access controls. Do not publish private artifacts to make review easier. Record authorized recovery location, access requirements and identity/fingerprint where applicable; a digest or ignored path alone is not transferable evidence.

## Identifying reviewed content

A snapshot is the identifiable substantive content at a gate, not a new storage system. Include the relevant Brief/Plan, adopted sources and decisions, plus plan/prerequisites, actual work and evidence as appropriate. Use existing commit IDs and paths, versioned artifact IDs or content hashes with recoverable content; for uncommitted changes a base commit plus exact relevant diff/untracked content identity can work **only if the reviewed content remains recoverable**. A hash alone does not preserve content. Preserve existing history/versioned artifacts; where needed use a scoped local preparatory commit or otherwise save just the relevant submitted material with existing project mechanisms. Distinguish preparatory preservation from accepted checkpoint. Do not require a duplicate copy when normal version history suffices. Ensure reviewer reads that identifiable version (freeze affected writes during review or provide pinned access). Record version pointers in actual review/approval and Task Ledger, and compare against actual current content before crossing the gate.

Separate lifecycle metadata (status, timestamp, decision pointer, completion bookkeeping) from substantive content; changes to claims about actual work, verification or obligation status are not exempt from completeness review merely because they occur in bookkeeping. Record what the reviewer/approver saw and why any metadata-only difference does not change it. Do not invalidate acceptance merely by recording acceptance. A Task Ledger append for review submission, invocation, response, checkpoint or closeout is lifecycle metadata only insofar as it adds no changed substantive claims or evidence. Pin the relevant submitted Ledger content when needed; do not freeze or suppress required later lifecycle events just to keep the file hash unchanged. Reconcile actual substantive/source changes and dependencies; no automatic carry-forward.

## Checkpoints

After Execution Acceptance create a durable checkpoint of accepted scope. Git default: local scoped commit of authorized relevant work; inspect diff/staging, exclude unrelated changes, verify commit content against accepted version. Check that every governing version and all required evidence/review records are durably recoverable; do not require them to be in the same repository or commit. Equivalent versioned artifact for non-Git work; multi-area Tasks may require several version references. Preserve review records/evidence/Task Ledger and their links; avoid circular commit self-reference (record verified commit ID afterward as an actual Task Ledger event, then persist record, not a rewrite of accepted substantive content). Before staging/committing or sharing, check the destination visibility and authorized data scope, including request/dialogue, review responses, private references and evidence; preserve sensitive artifacts and required originals via authorized recoverable private references, not a public commit. Push/publish only within actual authorization. If remote changes intervene, fetch/inspect, reconcile without overwriting others, verify reviewed content and any affected gates before pushing. Record material checkpoint and authorized push intent/outcome in the Task Ledger, distinguishing local persistence and verified remote state. Never force-push. Never stage unrelated files.

Retain recoverable reviewed content before requesting Execution Acceptance. Acceptance without verified checkpoint is pending. On interruption reconcile actual checkpoint, reuse matching existing one, or complete exact accepted checkpoint. If exact content cannot be recovered, report integrity blocker; do not replace it with unrelated content. Historical accepted checkpoints are never rewritten. Later correction has new identity and checkpoint. Final checkpoint covers same final content as both final reviews; record completion only after verifying all required records and checkpoint. Metadata-only completion recording is not a new substantive review.
